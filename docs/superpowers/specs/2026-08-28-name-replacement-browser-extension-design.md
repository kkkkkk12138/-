# 全网页小说阅读人名替换插件设计稿

日期：2026-08-28

## 目标

做一个浏览器插件，用户在任何网页阅读小说、同人文或长文本时，都可以用最简单的方式把主角名字替换成自己想要的名字。

这个插件的核心不是“规则引擎”，而是“无感替换”：

- 不要求用户改变已有阅读习惯
- 不要求用户切换到专门阅读器或导入文本
- 不要求配置复杂规则
- 点开插件弹窗即可修改替换项
- 保存后当前网页立即生效，并尽量保持视觉外观与原网页完全一致

## 非目标

第一版不做以下内容：

- 不做多层级高级规则面板
- 不做站点级规则管理中心
- 不做角色库、作品库、云同步
- 不做专门的阅读模式重渲染
- 不做覆盖层伪装替换
- 不承诺解决所有排版换行变化

## 用户场景

典型用户会在任意小说站、论坛页、同人站或文档型网页中直接阅读内容。当用户希望将主角姓名替换为自己偏好的名字时，只想点击浏览器工具栏中的插件按钮，在弹窗里填写“原名”和“替换成”，然后关闭弹窗继续阅读。

使用过程中，用户可能随时发现某个名字需要修正，因此希望再次点开弹窗就能编辑规则，并在当前页面立即看到变化，不需要刷新、不需要重新打开页面、不需要离开阅读界面。

## 产品原则

### 极简优先

用户只需要理解一件事：把原名改成新名。第一版交互不向用户暴露站点匹配、整词匹配、正则、优先级等概念。

### 无感优先

替换后的文本必须继承原网页已有的字体、字号、颜色、字重、斜体、行高与上下文样式。插件不主动改变页面视觉风格，不给替换结果包裹额外的装饰性样式。

### 兼容成熟生态

产品应默认把现有网页当成“阅读主场”，插件只是附着在浏览器上的轻型增强层，不抢网页本身的结构控制权。

### 内部保护，外部简单

虽然用户界面保持极简，但实现层必须内置误替换防护，避免因为“简单”而导致产品实际不可用。

## 方案选择

本项目采用“直接替换真实文本节点”的方案，不采用“覆盖层伪装”或“整页重渲染阅读层”。

原因如下：

- 只有直接替换真实文本节点，才能最大程度继承原网页已有样式，实现真正的视觉无感
- 覆盖层方案在复制、选择、换行、字重和动态内容场景下容易露馅
- 重渲染阅读层虽然更可控，但本质上会破坏用户已有阅读生态，与目标相反

## 信息结构

第一版插件信息结构尽量压缩为一个弹窗：

- 规则列表
- 每条规则包含两个字段：`原名`、`替换成`
- `新增一条` 按钮
- 每条规则的删除按钮
- 总开关：`本页启用`
- 主按钮：`立即生效`

可选但不外露为复杂设置的补充信息：

- 本页当前命中次数
- 上次生效时间

这些信息如果加入，也只能作为弱提示，不能扩大交互复杂度。

## 交互流程

### 首次使用

1. 用户打开任意阅读网页
2. 点击浏览器工具栏中的插件按钮
3. 在弹窗中新增一条或多条规则
4. 点击`立即生效`
5. 当前网页文本即时替换
6. 用户关闭弹窗继续阅读

### 阅读中修正

1. 用户阅读时发现替换名字需要调整
2. 再次点击插件按钮
3. 在原规则行中直接修改名字
4. 点击`立即生效`
5. 页面当前内容与后续动态加载内容继续按新规则替换

### 暂时关闭

1. 用户点击插件按钮
2. 关闭`本页启用`
3. 插件停止继续处理后续变动
4. 是否立即恢复原文，第一版建议不做自动回滚，只停止新增替换

不做自动回滚的原因是回滚需要缓存原始文本映射，复杂度和边界情况明显增加，不符合第一版极简目标。

## 核心体验要求

### 外观保持一致

替换完成后，页面文字在视觉上应尽量与原网页完全一致。实现上必须遵守以下要求：

- 不注入替换文本专用样式
- 不在命中文本外层包裹额外标签，仅在必要时改写文本节点内容
- 不修改段落、容器或排版相关 DOM 结构
- 不改变选择、复制、滚动、选中文本时的默认行为

### 生效速度快

用户点击`立即生效`后，当前可见区域的替换应尽快完成，主观感受接近“无等待”。在工程上应优先保证首屏和当前阅读区域的即时反馈，其余内容可在极短时间内补齐。

### 持续生效

对于无限滚动、分页注入、前端框架驱动的动态正文，插件需要持续监听新增文本并自动应用规则。

## 实现设计

### 整体结构

插件由三个部分组成：

- `Popup`：用户编辑规则与触发生效的弹窗界面
- `Content Script`：注入网页，负责扫描、替换与监听动态内容
- `Storage`：在浏览器本地保存规则与启用状态

### 数据模型

第一版数据模型保持最小：

```ts
type ReplaceRule = {
  id: string
  source: string
  target: string
}

type PageState = {
  enabled: boolean
  rules: ReplaceRule[]
}
```

说明：

- `id` 用于列表编辑和删除
- `source` 为原名
- `target` 为替换后的名字
- 第一版不加入站点维度、不加入别名数组、不加入高级匹配模式

### 替换策略

内容脚本只处理适合阅读的文本节点，不处理以下区域：

- `script`
- `style`
- `noscript`
- `textarea`
- `input`
- 可编辑区域
- 按钮控件文本
- 代码块与预格式区域

替换执行时遵循以下规则：

- 仅遍历文本节点
- 按规则源文本长度降序匹配，避免短词先命中破坏长词
- 同一节点内一次性完成替换，避免重复扫描抖动
- 优先处理当前文档中已经挂载的正文文本，再处理后续新增节点

### 动态内容监听

使用 `MutationObserver` 监听页面中的文本新增与结构变动。

监听策略需要克制：

- 合并短时间内连续变更
- 跳过明显与阅读无关的频繁更新区域
- 避免对整页反复全量扫描

目标是做到“内容来了就替换”，而不是“整页不停重跑”。

### 存储策略

规则和启用状态存储在浏览器本地。

第一版建议使用插件标准本地存储：

- 规则持久化，用户关闭浏览器后仍保留
- 启用状态默认按当前标签页生效逻辑处理

这里需要注意一个产品判断：

用户说的是“任何网页都可以用”，不是“所有网页默认都要替换”。因此第一版更合适的行为是：

- 规则是全局持久化的
- 是否启用由当前页面主动触发
- 只有用户点击`立即生效`后，本页才开始替换

这样既保证通用性，也避免用户打开普通网页时被全局误改文案。

## 误替换控制

虽然用户选择的是极简模式，但产品必须内置基础保护，否则真实体验会崩掉。

第一版内置以下防护：

- 空规则不生效
- 完全相同的原名与替换名不生效
- 长词优先替换
- 跳过表单和代码等非正文区域
- 跳过插件自身注入节点

第一版不做但后续可扩展的防护：

- 整词匹配
- 站点白名单
- 大小写策略
- 别名联动

## 性能要求

核心性能目标不是跑分，而是阅读无感。

第一版工程指标建议如下：

- 弹窗点击`立即生效`后，可见区域主观上近乎即时完成替换
- 页面滚动过程中，不因插件造成明显掉帧
- 动态内容替换不导致整页闪烁
- 规则数量在小规模场景下稳定可用，例如 1 到 20 条

第一版明确不追求“超大规则库”场景下的最优解。

## 风险与边界

### 排版重流

如果替换后的名字长度与原名字差距较大，网页换行可能发生变化。这不是样式被修改，而是正常排版重流。该问题在第一版不作为缺陷处理，但需要在产品认知上明确。

### 站点特殊渲染

某些站点会把正文拆成大量碎片节点，或在 Canvas、Shadow DOM、特殊前端框架容器内渲染内容。这些页面可能需要更细的适配策略。第一版不承诺覆盖全部特殊实现，但设计上应保留后续扩展空间。

### 误伤普通词

极简模式下，若用户输入的是高频普通词，可能会造成全页误替换。第一版通过基础防护降低风险，但不会引入复杂设置来完全消除该问题。

## 测试策略

测试重点围绕“无感”和“稳定”展开，而不是只验证功能通路。

### 功能测试

- 新增规则后本页立即生效
- 修改规则后当前页重新应用
- 删除规则后后续不再应用
- 关闭启用状态后停止处理新增内容

### 兼容性测试

- 静态 HTML 长文页面
- 无限滚动内容页
- 常见前端框架页面
- 含评论区、侧栏、导航的复杂页面

### 体验测试

- 替换后字体、字号、颜色保持原样
- 阅读时没有明显闪烁
- 滚动与选择文本行为正常
- 弹窗操作路径足够短

### 回归重点

- 同名短词误替换长词
- 动态内容重复替换
- 插件自身节点被再次处理
- 页面性能明显下降

## 里程碑建议

### 第一阶段：最小闭环

- 完成弹窗规则编辑
- 完成当前页静态文本替换
- 完成本地规则存储

### 第二阶段：阅读可用

- 加入动态内容监听
- 加入基本误替换防护
- 做页面节点过滤与性能优化

### 第三阶段：稳定打磨

- 修复特殊站点兼容问题
- 增加命中反馈与弱状态提示
- 视情况评估是否引入低学习成本的别名能力

## 结论

这是一个应当“看起来很小，但内核克制”的插件。

用户界面上，它应该像一个极简浏览器工具：点开，写名字，立即生效，继续阅读。

实现上，它本质是在做一个谨慎的文本节点替换系统：尽量不碰结构、尽量不改样式、尽量不打断动态网页的正常渲染。

第一版成功的标志不是功能数量多，而是用户在读文时几乎意识不到插件存在，只会感觉“名字已经自然换好了”。
