# 小说一键换名上架准备包设计稿

## 目标

为 `小说一键换名` 准备一套可用于浏览器插件正式上架的标准材料包，默认面向 `Chrome Web Store` 首次公开上架场景。
这套材料的目标不是“做一套夸张营销包装”，而是让插件在审核、理解成本和安装转化三件事上同时过关。

核心表达原则：

- 突出 `无感替换`
- 突出 `不改变阅读习惯`
- 强调 `规则保存在本地`
- 明确 `不会主动上传用户阅读内容`
- 对权限和能力解释真实、克制、可自洽

## 用户认知

目标用户不是技术用户，而是普通阅读者，尤其是有角色代入、CP 替换、同人阅读习惯的人。  
他们真正想要的不是“文本处理工具”，而是“在原来阅读网站里继续阅读，但主角名字已经变成自己想看的版本”。

因此商店文案不能从“查找替换”出发，而要从“阅读体验”出发。  
产品叙述应该让用户立刻理解三件事：

- 这是一个阅读场景插件，不是通用办公插件
- 它作用在当前网页，不要求导入文本或切换阅读器
- 它优先保证视觉无感，而不是做复杂的规则系统

## 上架策略

本次按 `标准上架包` 交付，不做最小凑提审版本，也不做完整营销站版本。

推荐原因：

- 最小包虽然省时间，但很容易在权限解释和商店素材上显得不成熟
- 完整营销包会把时间消耗在额外包装层，当前阶段收益不高
- 标准上架包正好覆盖审核、安装理解和基础转化三条线

## 交付范围

本次实际要产出的内容分为四组。

### 商店文案包

用于填写 Chrome Web Store 上架页面的核心字段，包含：

- 插件主名称
- 一句话副标题
- 简短介绍
- 详细介绍
- 卖点列表
- 常见问题简答版

写作要求：

- 语言真实，不夸大
- 避免“AI万能工具”式空话
- 围绕真实阅读场景组织表达
- 让用户在前两屏内理解“如何工作、为什么有用、有什么边界”

### 合规说明包

用于支撑审核和用户信任，包含：

- 隐私政策
- 数据使用说明
- 权限说明
- 不收集内容说明

重点要解释三个敏感点：

- 为什么需要 `storage`
- 为什么需要 `tabs`
- 为什么声明 `<all_urls>`

解释口径必须一致：

- `storage` 用于在本地保存替换规则
- `tabs` 用于识别当前活动网页并将规则应用到当前页
- `<all_urls>` 用于在用户主动打开的任意阅读网页中工作，而不是为了抓取浏览记录

同时要明确声明：

- 规则默认保存在浏览器本地
- 插件不会主动上传阅读页面正文
- 当前版本不依赖远程账号体系

### 素材与截图包

用于实际提交商店时的视觉素材准备，包含：

- 商店截图脚本
- 每张截图的标题与说明
- 建议截图顺序
- 图标使用说明
- 宣传卖点摘要

素材策略不是追求视觉花哨，而是追求“用户一眼看懂”：

1. 先展示规则编辑极简
2. 再展示页面替换前后
3. 再展示本页启用和动态生效
4. 最后展示边界说明或细节优势

### 提交辅助包

用于减少首次提审摩擦，包含：

- 上架检查清单
- 首次提审注意事项
- 容易被误判的点
- 驳回后常见修正方向

这部分重点不是平台流程教学，而是把当前插件最可能被问到的问题提前准备好答案。

## 文件产物

默认产出以下文件：

- `listing/chrome-web-store/store-copy.md`
- `listing/chrome-web-store/privacy-policy.md`
- `listing/chrome-web-store/permissions-and-data.md`
- `listing/chrome-web-store/screenshot-plan.md`
- `listing/chrome-web-store/submission-checklist.md`

如需补充视觉素材说明，可追加：

- `listing/chrome-web-store/assets-readme.md`

本阶段默认不直接生成商店截图图片本身，但会把截图脚本、镜头顺序和每张图的文案说明写完整，方便你下一步制作或让我继续生成。

## 内容风格

整体语气采用：

- 克制
- 清楚
- 少术语
- 少夸张承诺

禁止出现的表达倾向：

- “一键颠覆阅读体验”
- “AI 驱动全网改名神器”
- “适配所有网站所有场景”

推荐的表达方向：

- “在当前阅读网页里直接替换角色名字”
- “尽量保持原网站排版和样式不变”
- “规则保存在本地，打开网页即可使用”
- “适合小说、同人文等阅读场景”

## 审核风险点

这套包必须主动规避以下审核风险：

### 权限误解

`<all_urls>` 很容易让审核者担心插件读取过多内容。  
因此必须明确说明：只有在用户主动打开网页并使用插件时，内容脚本才会对当前页文本做本地替换处理。

### 数据处理误解

如果文案写得不清楚，审核方可能怀疑插件把阅读内容上传到服务器。  
因此隐私政策和权限说明中都要重复强调：当前版本不需要账号，不上传正文，不做云端同步。

### 功能边界模糊

如果把插件描述成“万能文本处理器”，审核和用户都会产生错误预期。  
因此必须限定主场景为“阅读网页中的角色名字替换”，而不是泛化为任意网页改写器。

## 非本次范围

本次不包含以下工作：

- Chrome 应用商店开发者账号注册流程
- 商店后台真实提交流程代填
- 宣传站页面开发
- 多语言商店文案
- 自动生成最终商店截图图片
- 法律顾问级别的隐私政策审定

这些可以在本包完成后继续扩展，但不放进当前第一轮交付。

## 验收标准

完成后的上架准备包应满足：

- 你可以直接把文案复制到 Chrome Web Store 对应字段
- 权限与隐私口径前后一致
- 用户读完首页说明后能明白插件是什么、怎么用、不会做什么
- 提交前你知道需要准备哪些截图、按什么顺序展示
- 出现审核质疑时，你已经有一版可直接回应的说明材料

## 建议顺序

建议按下面顺序生成实际文件：

1. 商店文案包
2. 合规说明包
3. 截图脚本与素材说明
4. 提交检查清单

这个顺序的原因是：文案和合规口径先定，后面的截图脚本和提审检查才能统一，不会反复返工。
